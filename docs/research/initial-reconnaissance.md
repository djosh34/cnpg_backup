## Architecture-shaping findings

1. PG18 can request an incremental physical backup by uploading a previous backup manifest. Its server uses local WAL summaries; required missing/expired summaries cause failure. Native incremental support began with PG17. [pg_basebackup](https://www.postgresql.org/docs/18/app-pgbasebackup.html), [continuous archiving](https://www.postgresql.org/docs/18/continuous-archiving.html#BACKUP-INCREMENTAL-BACKUP).
2. Using a full manifest as each reference yields differential-style dependency topology. This is an inference from the documented arbitrary earlier-reference mechanism, not a claim that PostgreSQL offers a distinct `--differential` option. Test this with exact PG18 images before adoption. Reconstruction uses `pg_combinebackup`; PostgreSQL does not manage retained parent dependencies for us. [pg_combinebackup](https://www.postgresql.org/docs/18/app-pgcombinebackup.html).
3. `pg_basebackup` stdout tar is restricted to no extra tablespaces and no WAL streaming. The simplest general native-tool path therefore has local staging costs. Restore needs extracted inputs and a synthetic output; optimized clone/link modes have restrictions. [pg_basebackup](https://www.postgresql.org/docs/18/app-pgbasebackup.html), [pg_combinebackup](https://www.postgresql.org/docs/18/app-pgcombinebackup.html).
4. The official Barman plugin already sends data to object storage without a traditional Barman backup server. Its manager mutates pods/jobs; sidecars execute instance and restore work, and CNPG owns Backup/ScheduledBackup. The replacement's differentiators are runtime/dependency footprint, backup-engine choices and testing, not inventing direct-to-object-storage topology. [Concepts](https://github.com/cloudnative-pg/plugin-barman-cloud/blob/v0.15.0/web/docs/concepts.md), [lifecycle source](https://github.com/cloudnative-pg/plugin-barman-cloud/blob/v0.15.0/internal/cnpgi/operator/lifecycle.go).
5. CNPG-I v0.6.0 exposes Backup, WAL Archive/Restore/Status/SetFirstRequired, lifecycle, identity and restore-job hooks. WAL requests include rewind context and destination-empty safeguards. Exact error mapping, lifecycle security/version requirements and recovery-target ownership need focused source tracing. [Protocol definitions](https://github.com/cloudnative-pg/cnpg-i/tree/v0.6.0/proto).
6. `minio-go/v7` has explicit static SignatureV2 and SignatureV4 credential providers. That supports considering it; it does not establish that all dependencies are CGO-free. Its v7.3.0 go.mod includes a large lint-tool dependency graph; inspect linked packages and final artifacts separately. [Static provider](https://github.com/minio/minio-go/blob/v7.3.0/pkg/credentials/static.go), [go.mod](https://github.com/minio/minio-go/blob/v7.3.0/go.mod).
7. Pure-Go filesystem chunking exists, e.g. [restic/chunker](https://pkg.go.dev/github.com/restic/chunker). That alone does not implement consistent online PostgreSQL backup or the catalog/GC/reconstruction it would require. The design preference for native increments is a trade-off recommendation, not a benchmark result.
8. PostgreSQL requires durable successful archive acknowledgment, permits identical durable retries, forbids overwriting differing archived contents, and notes async segment shipping may lag on quiet databases. `archive_timeout` reduces quiet-workload switching delay but cannot bound an S3 outage. [Continuous archiving](https://www.postgresql.org/docs/18/continuous-archiving.html).
9. A PITR target cannot be before the base backup has finished; timeline history and continuous required WAL matter. Therefore newest-backup selection and age-only retention are insufficient. [Recovery and timelines](https://www.postgresql.org/docs/18/continuous-archiving.html#BACKUP-PITR-RECOVERY).

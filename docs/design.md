# Direct-to-S3 CNPG backup plugin — implementation specification

Status: **final technical specification; independent reviews and an explicit READY resolution linking the frozen commit are required before implementation.** [Owner resolutions and READY](https://github.com/djosh34/cnpg_backup/issues/14) are authoritative. This document reconciles the scoped research into one contract; historical proposal/research wording is not a competing specification. [EXECUTE.md](EXECUTE.md) governs autonomous delivery, [pr-plan.md](pr-plan.md) the feature graph, [testing.md](testing.md) qualification, and [release-policy.md](release-policy.md) publication/security.

## 1. Binding owner decisions and support

- CGO-free Go runtime/dependencies; native PostgreSQL tools/libraries are the only justified native runtime exception. No Python/Barman/pgBackRest, custom replication engine, C archive extension, external backup server or replacement scheduler.
- Native full and **differential-to-full** backups: each differential references the exact original manifest of one retained full. Restore needs F+D2, never D1. A requested differential either succeeds as differential or fails; **no full fallback or fallback setting**, including missing summaries.
- PG18, primary capture, sidecars on all eligible instances for failover; CNPG-managed tablespaces and separate WAL volumes are mandatory, not optional implementation cuts. Standby capture, replica-cluster bootstrap, other majors/architectures and unmanaged layouts are outside initial support.
- Honest asynchronous archive RPO. Healthy profile `archive_timeout=60s` adds upload/queue latency; current segment/backlog can be lost, and outages have no fixed loss bound.
- Every plugin-managed restore, including cross-cluster/source-Kubernetes-loss recovery, automatically obtains repository-wide deletion protection before selection. Arbitrary external S3 readers are outside scope. Crashed/uncertain holds never expire; Warning events complement durable state. No elaborate lease/takeover service.
- Recovery window plus independent minimum-full floor; deletion off until configured, examples 14 days/two fulls; no independent aggressive WAL expiration.
- Last-success/failure monitoring separately for full/differential, implemented with those features.
- Automatically publish versioned releases and qualified images, **no production deployment**. Original project work is **all rights reserved**; preserve third-party licenses/notices without inventing a general project license.

## 2. Runtime topology and configuration

Use one Go executable with `manager`, `instance`, `recovery-job`, `recovery-guard` and `wal-fetch` modes, in two images. The manager is a one-replica Recreate Deployment beside the CNPG operator, using required mTLS; it reconciles configuration/lifecycle/status and bounded retention, never proxies data bytes. All database Pods and supported initdb/join/recovery Jobs get restartable init sidecars. Existing sidecars archive during manager outage. Use native CNPG Backup/ScheduledBackup/Cluster/externalClusters objects.

Plugin name/socket: **`cnpg-backup.djosh34.github.io`**, socket directory **`/plugins`**. Service discovery label **`cnpg.io/pluginName`**, annotations and certificate behavior are fixed in [CNPG contract §§2–5,9](research/cnpgi-contract-final.md). No files other than sockets go in `/plugins`. The recovery helper executable and nonsecret plan use separate small disk-backed bin/state volumes; secret projections mount only in the sidecar. Startup probe waits for the helper and socket, never for PostgreSQL or completed restore.

Use one namespaced **Repository** CRD, **`backup.cnpg-backup.djosh34.github.io/v1alpha1`**, structural schema/defaults/CEL and explicit validation. No conversion webhook, custom schedule/restore CRD or arbitrary pod templates. Generated ConfigMaps are delivery/status projections, not an editable second authority. Source and destination Repository resources are local to the target Cluster namespace; cross-cluster restore means a local source configuration pointing to the original S3 lineage.

### Canonical field names and selected limits

`Repository.spec` contains the storage fields shown in [storage contract §8](research/storage-protocol-final.md): `repositoryID`, `s3.endpoint/bucket/prefix/signature/addressing/region`, same-namespace `accessKeySecret` and `secretKeySecret` `{name,key}`, optional V4 `sessionTokenSecret`, optional `caConfigMap`, `encryption: bucket-default`, `compression: none|gzip` (gzip level fixed **1**), `io`, and `retention`. This naming replaces alternative field spellings in the initial CNPG research. TLS is mandatory, path addressing only, explicit credentials, no ambient chain, proxy, redirect or signer fallback. V2 with a session token is rejected.

Additional fields: `workspace` (generic ephemeral PVC `{storageClassName,size}` per Pod/Job), `native` budgets/settings below, Kubernetes `resources`, and optional `backupFreshness.fullMaxAge/differentialMaxAge`. The database-sized workspace must have verified finite disk backing/capacity; **ordinary emptyDir.sizeLimit is not a hard allocation limit and is not a supported database workspace**. Small helper/bin/state emptyDirs are distinct. No RWO workspace claim shared across all replicas. Every target PGDATA/tablespace/WAL filesystem also receives capacity preflight.

| Initial control | Default / hard supported maximum |
|---|---|
| `native.maxBackupBytes` (raw tar+manifest) | 32 GiB / 1 TiB; artifact also subject to storage's 512 GiB per-object cap |
| `native.maxBootstrapWALBytes` | 8 GiB / 256 GiB, included in raw backup budget |
| `native.maxRestoredBytes` | 32 GiB / 1 TiB, explicitly allocated among target volumes |
| Aggregate workspace ceiling | 256 GiB / 8 TiB; actual filesystem capacity and reservation must satisfy phase formula |
| Native manifest / file entries | **64 MiB / 100,000 per input** |
| Tablespaces / artifacts | **64 / 66** |
| Native path / regular file | 1,023 bytes / 1 GiB+1 MiB |
| `native.maxReferenceAge` / `native.captureTimeout` | 8 days (max 30 days) / 6h |
| Local native concurrency | One per instance/repository; never prevent WAL servicing |
| Data-path cgroup | 100m/256 MiB request; 2 CPU/3 GiB limit, **including native children** |
| I/O deadlines/concurrency | Storage §3: 10s connect, 30s metadata, 15m data request, 24h whole operation; two WAL slots independent of two artifact streams/two part workers |
| Source WAL recovery helper | Sidecar read/retry budget 60s, helper deadline 75s; exhausted errors exit255 |

These stricter native caps are the actual initial supported envelope, not the broader serialization ceilings in the storage research. Missing/invalid configuration fails validation; exceeding runtime budgets fails without publication/startup. Budget increases within supported maxima are ordinary configuration, not performance guarantees. Reject unknown fields, unsafe TLS, force-clear/TTL, fallback, external-reader workflow and arbitrary compressor options.

`Backup.spec.target` and ScheduledBackup target must be **primary**. Per-backup parameters contain only required `backupType: full|differential`; missing type never silently schedules a full. Cluster plugin parameter `repository` selects destination; external-cluster plugin parameter `repository` selects source. CNPG owns status and target replay; advertise only implemented capabilities. WAL Status/SetFirstRequired are unimplemented/unadvertised initially because this operator does not call them; retention never depends on them.

## 3. Native capture, authentication and reconstruction

The exact tool commands, archive verification, tablespace mapping and workspace formulas are in [native workflow §§1–6](research/native-workflow-final.md), with the compressed-spool reconciliation recorded there. Runtime native allowlist: `pg_basebackup`, `pg_verifybackup`, `pg_combinebackup`, `pg_waldump`, `pg_controldata`, `psql` and their scanned libraries. No production shell compression/extraction or native incremental-header parser.

Authenticate as CNPG's **`streaming_replica`** role using the replication client certificate; `cnpg_streaming_replica` is the ident map, not the role. Use verified Service SAN as libpq `host`, **`hostaddr=127.0.0.1`** to pin the actual selected local primary, and a private fixed service/cert snapshot. Two replication connections/one temporary slot are reserved for `-X stream`. No superuser/password fallback. Fixed public SQL queries supply role/settings/time/postmaster state; obtain privileged control identity/checksum details using `pg_controldata` on mounted/extracted control data rather than assume extra SQL privileges. Native pre/post identity and CNPG selected instance must agree.

Capture sequence:

1. Acquire the repository backup holder, validate identity/config/physical layout and capacity, freeze UID request/root. Store capture Pod UID and postmaster start time in commit metadata so a later differential can reject loss of checksum-state continuity after server restart.
2. `pg_basebackup --format=tar --wal-method=stream --checkpoint=spread --manifest-checksums=SHA256`; differential adds only the exact full `--incremental` manifest. No stdout tar, skip-checksum, no-sync or no-manifest options. Fail on promotion, restart/identity/checksum/timeline mismatch or missing summaries. Example `wal_summary_keep_time=14d` must exceed maximum reference age + capture deadline + 24h slack; actual summary coverage remains PostgreSQL's check.
3. Preserve original manifest; scan archive structure/counts/paths/byte limits in Go before passing input to native verifiers, then verify tar full/incremental with `pg_verifybackup --no-parse-wal`. Safely extract only bundled WAL and needed small control metadata for capture checks; validate every manifest WAL range using matching `pg_waldump`. Bundled WAL is not individually covered by manifest file checksums.
4. Scan/validate archive structure, write bounded compressed spool, compute exact raw/stored sizes and SHA256, and upload known-length files with explicit Core multipart operations. Verify completed artifacts and postflight before conditional commit-last publication. Cancellation kills/reaps process groups and never commits incomplete data.
5. Commit does **not** wait for a second archive-namespace copy of bundled WAL. Uploaded verified bootstrap WAL makes the base self-contained, not continuously PITR-covered. Retain original start/end LSNs and source-server completion upper bound separately from later S3 publication time.

Every `pg_verifybackup` invocation (tar, extracted originals and synthetic output) uses **`--no-parse-wal`**; Go `exec.Command` invokes matching `pg_waldump` directly for **each validated manifest WAL range**. The verifier's default WAL path calls `system()` and would require a forbidden shell in the data image; disabling that path does not skip WAL verification ([R0 correction](research/review-corrections.md)). Restore verifies each original F/D input **before** combining. A real negative control demonstrated that combine plus synthetic verification alone can bless corrupted input. Extract with confined, bounded Go filesystem operations into isolated roots; reject archive-provided links/devices/traversal/duplicates/sparse encodings, then create only trusted native-layout links. Input WAL stays a directory. Ordinary-copy `pg_combinebackup F D2` maps each D2 tablespace from its extracted link target; D1 is absent. Verify the synthetic result, then perform explicit bootstrap transforms: remove verified historical `tablespace_map`, construct target-owned mappings, relocate/sync WAL to the separate volume, and generate target recovery configuration. Never start PostgreSQL on partially transformed data.

**Target ownership starts before CNPG's main command**, whose pre-RPC preflight can rename/remove PGDATA and WAL. Lifecycle wraps the original recovery argv with the narrow Go `recovery-guard` mode, PID1 in the main container's private PID namespace. Before starting CNPG it acquires exclusive advisory locks and fsyncs fresh durable owner markers in private `.cnpg-backup` directories outside data directories on every target PVC (PGDATA, WAL, tablespaces; stable PVC-UID lock order). Immutable volume sets cannot overlap another Cluster's writers. Busy lock means active owner; **any existing marker after acquiring locks means poisoned/uncertain ownership**, even for a dead PID. Never infer safe takeover from PID death, elapsed time or Pod deletion. Retry a poisoned target using a fresh Cluster and fresh target PVCs, not marker removal.

The guard retains ownership through preflight, materialization, delayed RestoreResponse, replay, CNPG exit, all PostgreSQL descendants and sidecar target-write drain. A tiny local Begin/Drain control session on the existing Unix socket binds Pod UID + guard UUID + sidecar process UUID; sidecar admits no target work before Begin, rejects stale identities and irreversibly closes admission before acknowledging drained writes/subprocesses. Guard release requires all main-namespace descendants reaped **and** that same sidecar's clean drain; sidecar/session/guard crash or uncertain termination retains markers. A sidecar restart cannot adopt the session. Clean release removes/fsyncs markers while locks remain held, then unlocks. No sidecar-held lock, generic service, process-group-only descendant assumption or Job API status substitutes for this local fence. Exact argv, startup/probe and termination semantics are in [CNPG target ownership](research/cnpgi-contract-final.md#target-ownership-before-the-main-command-ks2-correction). Require working local/block filesystem locking/fsync; shared-NFS semantics and unguarded/reused target writers are unsupported. Source S3 admission remains separate.

Workspace accounting includes raw archives **and** compressed spool, extracted bundle, metadata/allocation overhead and `max(1GiB,10%)` free-space margin. Differential restore reserves compressed F+D, extracted F+D, explicit full-output maximum and duplicated WAL during cross-volume copy. Validate per-filesystem limits, not only aggregate bytes. A fixed-size filesystem/quota is the hard native-writer stop; polling/emptyDir eviction alone is not. Source PGDATA is never staging disk.

## 4. Repository publication and global deletion admission

Adopt the concrete **v1 schema, key layout, conditional operations, ownership, retirement and retry algorithms in storage §§3–8**. The repository module owns these details behind a small interface; callers never construct keys or reorder commit/deletion steps. Specific reconciliations in this document are binding.

- Immutable repository UUID/system/PG/WAL-segment/writer-Cluster identity; UUID is a lineage, not Cluster name or system ID alone. A restored cluster always archives into a distinct destination UUID. One cooperative writer cluster per repository. Unversioned/no-Object-Lock buckets only; no lifecycle expiration or unrelated mutators. Source restore requires prefix reads/list plus exact `gate.json` Get/Put, not payload deletion or surviving source Kubernetes.
- Conditional shared-name single PUTs use `If-None-Match:*`; gate/retires use ETag CAS, never ETag-as-checksum. The backend must provide atomic conditional writes, atomic visibility and strong reads/lists. Actual MinIO tests passed for V2/V4/private CA. Other endpoints must document/pass that capability contract; fail `UnsupportedStorageSemantics`, never HEAD-then-PUT fallback.
- Backup UID `request.json` freezes semantic input; random attempt claims own artifact keys; first valid immutable commit wins. A loser/retry validates and returns the winning durable result, not its own different bytes. Preserve permanent commit/request/retired metadata. Added commit fields: `capture_instance_uid`, `postmaster_started_at`; preserve native ranges/tablespace/label metadata described above. Last-success uses the immutable commit object's S3 LastModified publication timestamp; source capture completion remains selection/status metadata, not that timestamp.
- Use SDK Core multipart primitives so SDK error-path automatic abort cannot delete outside admission. WAL uses a seekable spool and conditional single PUT; never whole-WAL MD5 buffering through a gzip pipe. Acknowledge only durable bytes or verified identical live content. Same name/different content is fatal. No early-ack queue.
- One small CAS `gate.json` contains a generation/unique nonce, nonexpiring holders, and either no owner or one process-specific GC owner. Holders and GC owner are mutually exclusive. Add-holder CAS success is acknowledged admission; stale gate requests are fenced by ETag/nonce transitions, including an explicit no-op CAS barrier after ambiguous outcomes. No source controller, distributed lease or fencing-by-clock assumption.
- A GC owner never expires or transfers across process incarnation. It serially retires/deletes/aborts, disables blind SDK/proxy retries, and releases only after **every dispatched destructive request conclusively drains**. A response to a retry/HEAD absence is not proof an earlier request drained. Ambiguity/crash leaves owner set and blocks new admission. This is an explicit fail-closed availability boundary, not a promised automatic repair.
- Crashed backup/restore holders block GC but **do not block other admitted backups/restores**. Never erase a different process's uncertain hold. Holds/tombstones/history may accumulate; capacity exhaustion fails clearly. No forced-clear setting. Warning events/status explain `RetentionBlocked`/`RepositoryAdmissionBlocked`; they are not lock state.

Retirement permanently excludes a backup before payload deletion; immutable commit remains for diagnosis. WAL payload is replaced at the **same permanent key** with a conditional tombstone, never physically deleted/reused, so late no-clobber uploads cannot resurrect it. Orphan payload deletion/MPU abort also requires exclusive GC admission. All error paths own cleanup explicitly; conservative leakage is preferable to a false durable acknowledgment or deleted dependency.

## 5. Restore lifecycle and PITR

Pinned CNPG runs primary recovery **inside the recovery Job**: the plugin materializes, CNPG starts PostgreSQL/replays/waits for recovery completion/stops it and writes ordinary destination replication settings. The old proposal's download-only Job model is superseded. Follow [CNPG §§2–3,7–8](research/cnpgi-contract-final.md).

### Durable plan and lifetime

The operation ID is a deterministic UUID derived from target Cluster UID and immutable bootstrap fingerprint. Manager persists the operation/terminal state in an owned nonsecret per-Cluster ConfigMap (also the config projection), using resourceVersion updates; no sidecar ConfigMap-write RBAC is required. It obtains the stable source restore-lifetime holder before work. For races/retries, a sidecar must positively establish that holder plus its **own fresh process-reader holder** before any catalog/data read; the shared gate is authoritative even if projection delivery lags.

Sidecar persists its selected plan atomically on the target PGDATA **volume outside actual PGDATA**, `.cnpg-backup/<operation>/recovery.json`, before materialization, and projects a copy to `/cnpg-backup/state/recovery.json` for the helper. It contains source/target identity, exact chain/target/frontier/hold IDs and no credentials. New process attempts reacquire their own holder and reuse a validated persisted plan, or choose a new plan only under a newly acknowledged lifetime/admission. No Kubernetes Backup catalog is needed. New target PVC/config after disaster can create its own protected plan from S3.

Returning RestoreResponse does not release protection. Source WAL helpers use the admitted plan through replay, failure and injected pause. On graceful reader shutdown, that **same process** closes callback admission, drains tasks/requests and releases only its own reader holder; a crashed or uncertain reader hold remains. The manager marks the operation terminal and releases the **stable lifetime holder only** after matching Job Complete and all matching/retry Pods/containers have reliably terminated, with operation identity checked. It never clears another process-reader holder based on Kubernetes status. Unknown/force-deleted/disappeared Job evidence retains protection. Completed operations are rejected by lifecycle validation and source helpers; any genuinely new restore reacquires protection. Normal instance/rewind mode reads destination storage only, never the retained source externalCluster. This permits normal automatic release without assuming Pod deletion fences an old source reader.

### Missing versus failed WAL

CNPG v1.30 collapses plugin WAL errors to ordinary exit1. That is unsafe for latest primary recovery. Return a constant **direct Go `wal-fetch` restore_command** from RestoreResponse; helper is copied atomically before main startup, uses the existing Unix WAL RPC, and has no S3 credentials. Exact quoting/paths are fixed in the CNPG contract.

- Verified durable file: **exit0**.
- Authenticated missing future-tail/history file, not required by the plan: **exit1**. Also **exit1** for a missing archive duplicate when the requested bundled file is verified still available in local `pg_wal` and no required post-backup bytes in that segment depend on the archive. PG18 tries archive **before** local WAL: this ordinary miss permits its native local fallback.
- Plan required coverage is **per timeline/LSN interval**, not just filename membership: selected bundle covers only its manifest ranges; any segment intersecting required post-backup coverage through the admitted archive frontier is remote-required, including the final bundled segment. Its archive absence is **255**, never hidden by zero-padded bundle bytes. Prefer verified archive contents whenever present; never return a bundle as archive success to truncate later data. Explicit targets still must be reached by PostgreSQL.
- Required gap, corruption, retired data, TLS/auth/timeout/transport/gRPC/invalid-plan error, exhausted bounded retry or helper panic: **exit255**, even when a bundle exists. The initial implementation always attempts source archive lookup (including immediate); no speculative local-success or outage-to-miss shortcut. Never pass through generic Cobra exit1. The sidecar alone issues NotFound for the allowed ordinary-miss cases after validating local availability and required ranges ([S1 details/evidence](research/review-corrections.md)).

Archive/restore names and destinations are validated before I/O. Restore downloads into a private file, verifies gzip/raw size/SHA256, fsyncs, atomically publishes and syncs its directory. No prefetch/negative cache; rewind is exact-file safe. Old absent optional CNPG-I guards default safe, never disable destination ownership/no-clobber. Ordinary standby/rewind uses CNPG's existing command and may retry/fall back to streaming; that is not a supported external-source latest-recovery path.

### Target selection

Use a complete valid committed catalog and numeric source timeline/history path, under protection. Omitted timeline resolves a unique latest descendant at admission; ambiguous leaves require numeric `targetTLI`. Explicit `current/latest` strings are rejected because CNPG would override the frozen numeric setting. Selected base must predate any relevant fork and target; no newest-base shortcut.

- Latest: newest usable base (or exact backupID), continuous known archive through admission frontier; a hole before frontier is fatal. True future misses may end replay. No claim of latest unarchived transaction.
- Time: timezone-qualified RFC3339; conservative source-server capture completion **strictly before** target.
- LSN: numeric native end LSN **strictly before** target on the selected path.
- Named point/XID/immediate: explicit backupID; names unique in supported workflow, XID a known top-level committed transaction without wrap ambiguity; no inferred time ordering. Immediate means selected base's first consistent point, not latest.
- Preserve CNPG inclusive/exclusive options for time/LSN/XID; reject invalid combinations. Initial action is **promote** (CNPG has no action field). Injected pause remains protected, not silently resumed by the plugin.
- PostgreSQL enforces reaching the target. Download/combine/RPC success is not PITR success. Full or selected differential plus forward WAL across valid timelines is supported; differential **capture** after a timeline/checksum/restart transition requires a new explicitly requested full.

## 6. Retention and observability

Apply the deterministic planner/deletion sequence in storage §7: keep backups inside the window, a usable pre-cutoff anchor per lineage, minimum full roots, and full-parent closure. Preserve the last usable root even after prolonged failed backups. Keep WAL from the earliest required redo/start/fork floor, never object age or lexical cross-timeline ordering. First release conservatively retains non-current-timeline WAL and history indefinitely. Unknown metadata, partial lists, missing required coverage or uncertain operations stop destructive work and report degraded coverage.

`retention.enabled=false`, `dryRun=true` initially. Explicit window (1h–3650d), minimumFulls (1–100), interval (5m–24h, default1h); example 14d/two roots. A batch owns the gate before authoritative inventory, performs at most128 serial destructive requests or30s between acknowledged requests, drains/releases, yields at least1s. This is work batching, **not lease expiry**. Replan safely after conclusively completed batches; ambiguous owners cannot be resumed by another process merely from a GC log.

The single manager owns bounded Prometheus labels `{repository_id,namespace,cluster,backup_type}`, type only full/differential. `cnpg_backup_last_success_timestamp_seconds` comes from durable commit history/publication time (including permanent metadata of subsequently retired backups, since expiration does not erase historical success), not restart time or failed attempts. Omit unknown/never-successful values and expose `cnpg_backup_success_history_known`. `cnpg_backup_failures_total` counts each observed transition of a Backup UID to terminal failed once per manager process lifetime; initial informer sync establishes a baseline, requeues/resync/S3 retries do not increment, missed downtime transitions are not fabricated. A durable commit with lost CNPG response can legitimately produce both committed-success freshness and a failed invocation count; expose disagreement, never discard valid data to match status.

Ship Warning `BackupFailed`, separate full/differential missing/overdue/failure alerts enabled only for configured schedules, plus independent WAL backlog/failure/filesystem pressure alerts. No ID/key/error-string metric labels or durable metrics ledger. These ship in full/differential PRs, not only final operations work.

## 7. Security, test evidence and adaptation

Narrow namespace/RBAC and Secret get-only allowlists, non-root matching CNPG UID, read-only root, dropped capabilities/seccomp, same-namespace explicit projections, and no application/superuser/private-server-key mounts. Manager cert-manager mTLS and leaf/CA reload follow exact pinned CNPG behavior. New operations load a complete validated Secret/CA snapshot; running work retains its snapshot, so credentials/trust overlap must last through draining work. An invalid rotation fails closed rather than using stale credentials indefinitely or dropping holds.

[Release policy](release-policy.md) fixes endpoints, immutable publication, licensing, scans/SBOM/provenance and resource evidence. [Testing](testing.md) requires per-feature tests, real-module DST with independent oracles, fuzzing, and actual CNPG/PG18/MinIO SQL recovery at exact subject image digests. Post-backup archive replay and missing/corrupt required-segment failures, failover, both signatures/private CA, tablespaces/separate WAL, retries/retention/restore races and metrics are mandatory. First release has no predecessor; it establishes fixtures, not a fake upgrade result.

Planning evidence is already concrete: [native full/F+D2/PITR and corruption experiments](research/native-workflow-final.md), [real SDK conditional/multipart and bounded gate exploration](research/storage-protocol-final.md), [PG fatal-versus-EOF negative control and source contract](research/cnpgi-contract-final.md), [publication/OIDC/platform preflight](research/platform-preflight.md). This is **not product qualification**. The production integrations must repeat and extend those distinguishing tests.

Initial concrete modules: `cnpgi` translates hooks; `repository` owns identity/publication/catalog/admission/plans; `postgres` owns controlled tools/native workflow; `wal` owns one-file archive/restore; `retention` separates pure keep/delete planning from revalidated execution; `s3store` wraps the actual SDK. These are internal seams, not a plugin framework. Simulators/fault scheduling live in tests. After READY, ordinary code/PR boundary changes and evidence-driven internal corrections are autonomous, with recorded rationale and regressions, never hidden safety reductions or new routine owner approvals.
